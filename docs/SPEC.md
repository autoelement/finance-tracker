# FIN — ფუნქციონალის სპეციფიკაცია

> ეს დოკუმენტი აღწერს სისტემას სრულად. გამოდგება როგორც დავალება (პრომპტი)
> ნულიდან ასაწყობად, ისე მოქმედი სისტემის დოკუმენტაციად.

---

## 1. რა არის

ბიზნესის ფინანსების აღრიცხვის ვებ-აპლიკაცია. ტრანზაქციებს **ავტომატურად იღებს
ორი ბანკის API-დან** (საქართველოს ბანკი და თიბისი), ანაწილებს შემოსავლებად და
ხარჯებად, არისხებს მომხმარებლის კატეგორიებში დანიშნულების მიხედვით და აჩვენებს
მოგება/ზარალს, სტატისტიკასა და გრაფიკებს.

**მასშტაბი:** ერთ ანგარიშზე **500 000 – 700 000 ჩანაწერი**. ეს არ არის
თეორიული — ყველა არქიტექტურული გადაწყვეტილება ამ რიცხვითაა ნაკარნახევი.

**ინტერფეისის ენა:** ქართული. კოდი და კომენტარები — ინგლისური.

## 3. მონაცემთა მოდელი

```
transactions   id, user_id, import_id, dedup_key, txdate (date), descr,
               category, ttype ('income'|'expense'), amount (>0),
               bank, manual (bool), match_text
               UNIQUE (user_id, dedup_key)

finance_state  user_id, cats (jsonb), imports (jsonb)

fin_summary    user_id, mkey ('YYYY-MM'), category, ttype,
               total, cnt, dmin, dmax
               PRIMARY KEY (user_id, mkey, category, ttype)

sync_state     user_id, bank, last_day, last_run_at,
               last_status, last_error, last_added

bank_credentials  user_id, bank, base_url, accounts, client_id,
                  token_url, scope, auth_mode, secret_id → vault
```

**ყველა ცხრილს RLS ჩართული აქვს** პოლიტიკით `user_id = auth.uid()`.

`amount` ყოველთვის **დადებითია**; მიმართულებას `ttype` ატარებს.

## 4. ავტორიზაცია

- Supabase Auth, მეილი + პაროლი. შესვლა და რეგისტრაცია ერთ ეკრანზე, გადამრთველით.
- თითოეული მომხმარებელი მხოლოდ თავის მონაცემებს ხედავს (RLS).
- ჰედერში: ინიციალების ავატარი (დასაკლიკებელი, შესაცვლელი), გასვლა.
- ინიციალები ინახება `localStorage`-ში — **ყველა წვდომა try/catch-ში**, თორემ
  ინკოგნიტო რეჟიმში გამონაკლისი შესვლას აფერხებს.

## 5. მონაცემების წყარო

### 5.1 ბანკების API (ძირითადი)

**BOG** — `GET {BASE}/api/v2/statement/{account}/{currency}/{from}/{to}?page=N`
გვერდზე 1000 ჩანაწერი. ანგარიშზე მიბმულია, ანუ თითო ანგარიში ცალკე იკითხება.

**TBC** — `GET {BASE}/bab/v1/accounts/movements?PeriodFrom=…&PageIndex=N`
გვერდზე 700. ანგარიშის მითითება არასავალდებულოა (ცარიელი = ყველა).

**ავთენტიფიკაცია:** OAuth2 `client_credentials`. ტოკენი ქეშირდება ვადის
ამოწურვამდე 60 წამით ადრემდე. სამი რეჟიმი, რადგან ბანკები განსხვავდებიან:
`oauth_basic` (Basic ჰედერი), `oauth_body` (სხეულში), `header` (გაცვლის გარეშე).

**ველების რუკა:**

| ჩვენი | BOG | TBC |
|---|---|---|
| `dedup_key` | `BOG\|entryId` | `TBC\|movementId` |
| `txdate` | `entryDate` | `date` |
| `ttype` | debit/credit | `isDebit` |
| `amount` | `entryAmount…Base` (ლარში!) | `amount` |
| `descr` | `documentNomination` | `purpose` |
| პარტნიორი | `senderDetails` / `beneficiaryDetails` | `partnerAccountInfo.partnerName` |
| ტიპი | `documentProductGroup` | `transactionType` (კოდი → ლეიბლი) |

**TBC-ის `statusCode`:** მხოლოდ `0` (ავტორიზებული) ითვლება. `1` და `2`
ავტორიზაციას ელოდება — ფული ჯერ არ გასულა, შემდეგ სინქრონზე აიღება.

### 5.2 ექსელის იმპორტი (ისტორიული)

ყოველდღიური ნაკადიდან **მოშორებულია** — მხოლოდ პარამეტრებში, „ისტორიული
მონაცემების შემოტანა". მიზეზი: API შეზღუდულ ისტორიას იძლევა.

- ბანკი ირჩევა ატვირთვისას (BOG / TBC / სხვა)
- სვეტები ამოიცნობა **სათაურის ტექსტით**, არა პოზიციით
- „სხვა" ბანკზე — ხელით შედარების ფანჯარა წინასწარი ხედით
- თარიღის ფორმატი ბანკზეა მიბმული პარამეტრებში (BOG: MM-DD-YY, TBC: DD-MM-YY)

### 5.3 ხელით დამატება

ცალკე ფორმა: თარიღი, დანიშნულება, კატეგორია, ტიპი, თანხა, ბანკი.
ინახება `manual: true`-თი და **ხელახალი კატეგორიზაცია მათ არ ეხება**.

## 6. კატეგორიზაციის ძრავა

**ერთი იმპლემენტაცია** `shared/categorize.js`-ში, რომელსაც **ორივე**
იყენებს — ბრაუზერიც და sync სერვისიც. ორი ასლი გაიყრება და გაყრა უხილავია:
ციფრები უბრალოდ არასწორი გახდება.

- კატეგორიას აქვს: სახელი, ტიპი (`income`/`expense`/`any`), **საკვანძო
  სიტყვები**, **გამონაკლისები**, და ჩამრთველი **„ითვლება ანგარიშებში"**
- ემთხვევა **პირველი** წესი → სიის რიგი არის პრიორიტეტი
- ემთხვევა, თუ `match_text` შეიცავს საკვანძო სიტყვას **და არ შეიცავს**
  არცერთ გამონაკლისს (ამით იყოფა თითქმის იდენტური დანიშნულებები)
- ვერაფერს ემთხვევა → `სხვა`

**19 ნაგულისხმევი კატეგორია** (რიგი = პრიორიტეტი): მძღოლებზე გაცემული,
ბანკის საკომისიო, იანდექსი, კომუნალური, პროგრამული უზრუნველყოფა, მარკეტინგი,
საბიუჯეტო გადასახადი, ონლაინ გადასახადები, აღჭურვილობა, ინვენტარი,
თანამშრომელთა ხელფასები, საოპერაციო ხარჯები, მოგების განაწილება, კომპენსაცია
პარკებს, საკომისიო პარკებიდან, ახალი მძღოლების საკომისიო, პრო პაკეტის
შემოსავალი, ბალანსის შევსება, სხვა.

**„არ ითვლება" კატეგორია:** არცერთ ჯამში არ მონაწილეობს, მაგრამ **ჩანს**
სიაში ნაცრისფრად, ნიშნით „არ ითვლება", თავისი რეალური თანხით. სრულად დამალვა
მომხმარებელს აბნევს — ფიქრობს, მონაცემი დაიკარგა.

## 7. ინტერფეისი

ხუთი ჩანართი: **დეშბორდი · თვეები · კატეგორიები · ისტორია · პარამეტრები**

### 7.1 დეშბორდი

პერიოდის ამომრჩევი (ყველა / კონკრეტული თვე). **იხსნება ბოლო თვეზე**,
რომელშიც ჩანაწერია — არა „ყველა პერიოდზე".

**KPI ბარათები:** შემოსავალი, ხარჯი, ნეტო (+ მარჟა %), პერიოდი, ჩანაწერების
რაოდენობა. ჩატვირთვისას — **skeleton ანიმაცია**.

**5 გრაფიკი:** მოგება/ზარალი თვეებში, შემოსავალი vs ხარჯი, ხარჯები
კატეგორიებად (doughnut), შემოსავლები კატეგორიებად, კუმულატიური ნაშთი.

**კატეგორიების ჯამები:** კატეგორია · ტიპი · რაოდენობა · თანხა. დაკლიკებით
ფილტრავს ტრანზაქციების ცხრილს. ბოლოში — „არ ითვლება" კატეგორიები.

### 7.2 ტრანზაქციები

სერვერული გვერდიანობა (500 სტრიქონი). ფილტრები: ძებნა დანიშნულებაში, ტიპი,
კატეგორია, ბანკი, **ითვლება/არ ითვლება**. დახარისხება ყველა სვეტზე.
კატეგორია ცხრილშივე იცვლება ჩამოსაშლელით.

**ყველა ფილტრი ერთი ფუნქციით იწყობა** — ცხრილი, მთვლელი და CSV ექსპორტი
ერთსა და იმავეს იყენებენ, თორემ გაიყრებიან.

**CSV ექსპორტი:** პარალელური გვერდებით, სვეტით „ანგარიშებში ითვლება?".

### 7.3 თვეები

თვეების სია (ქართული სახელებით: „ივნისი-2026", არა „2026-06"), თითოეული
ჩამოსაშლელი — შემოსავალი, ხარჯი, ნეტო, კატეგორიების დაშლა.

### 7.4 კატეგორიები

დამატება, წაშლა, ტიპის შეცვლა, საკვანძო სიტყვები (chip-ები), გამონაკლისები,
„ითვლება ანგარიშებში" ჩამრთველი. ღილაკი **„ხელახალი კატეგორიზაცია"** — ყველა
ჩანაწერს გადაარისხებს ახალი წესებით (ხელით შეცვლილებს არ ეხება).

### 7.5 ისტორია

იმპორტების სია: თარიღი, ბანკი, ფაილი, ჩანაწერები. **ჩანაცვლება** და
**წაშლა** თითო იმპორტზე. ხელით დამატებულების ჩამოშლა — თითოს ცალკე წაშლით.
**სრული წაშლა არ არსებობს** — მონაცემები ისტორიულად ინახება.

### 7.6 პარამეტრები

- თარიღის ფორმატი ბანკების მიხედვით
- **დათვლის რეჟიმი** — ⚡ სწრაფი / 🐢 სარეზერვო, + ბოლო შეცდომის მიზეზი
- **ბანკების კავშირი** — Client ID, Secret, token URL, რეჟიმი, ანგარიშები
- **ისტორიული მონაცემების შემოტანა**
- **ჯამები** — იძულებითი გადათვლა, შემოწმება

## 8. წარმადობის არქიტექტურა

ეს არის სისტემის გული. 575 000 ჩანაწერზე გულუბრყვილო მიდგომა არ მუშაობს.

**წინასწარ დათვლილი ცხრილი `fin_summary`** — თვე × კატეგორია × ტიპი.
რამდენიმე ასეული სტრიქონი ნახევარი მილიონის ნაცვლად. დეშბორდის ყველა ციფრი
მისგან გამოითვლება **მეხსიერებაში**, ანუ თვის გადართვა მყისიერია.

**სერვერული ფუნქციები** (`sql/setup.sql`): `fin_rebuild_summary`, `fin_kpi`,
`fin_monthly`, `fin_by_category`, `fin_daily`. **ყველა მათგანი
`transactions`-იდან კითხულობს**, არა `fin_summary`-დან — თორემ შემოწმება
ცხრილს თავის თავს ადარებს და ვერასდროს დაიჭერს შეცდომას.

**ინკრემენტული განახლება:** იმპორტის ან წაშლის შემდეგ ჯამები **არ** გადაითვლება
სრულად — მხოლოდ შეხებული სტრიქონები ახლდება.

**თვის გადათვლა:** თუ ერთი თვე არ ემთხვევა, მხოლოდ **ის თვე** გადაითვლება —
მისი დღეები 6 ნაკადად პარალელურად. სრული სკანირება მხოლოდ ხელით ღილაკზე.

## 9. კორექტულობის ინვარიანტები

> ეს სია შეცდომების ფასად დაიწერა. თითოეული პუნქტი რეალური ბაგია, რომელიც
> პროდაქშენში მოხდა.

1. **supabase-js builder ზარმაცია.** `.then()`-ის გარეშე მოთხოვნა
   **საერთოდ არ იგზავნება**. RPC-ის `.then()`-ის დავიწყება ნიშნავს, რომ
   გადათვლა არასდროს მოხდა, შეცდომის გარეშე.

2. **PostgREST აბრუნებს მაქსიმუმ 1000 სტრიქონს.** გვერდიანობის გარეშე
   ჯამები ჩუმად იკვეცება.

3. **გვერდიანობა `ORDER BY`-ს გარეშე არასწორია.** Postgres რიგს არ
   გარანტირებს — პარალელური გვერდები ერთმანეთს ფარავს (დუბლიკატები) და
   სტრიქონებს ტოვებს. ყოველთვის `.order("id")` + id-ით დედუპლიკაცია.

4. **ღრმა `OFFSET` timeout-ს იწვევს.** Keyset გვერდიანობა
   (`.gt("id", lastId)`), არა `.range()`.

5. **თარიღი კალენდარულია, არა მომენტი.** ბანკი `+04:00`-ს აგზავნის ან
   არაფერს; UTC-ზე გადაყვანა საღამოს ტრანზაქციას წინა დღეში გადაიტანს.
   ვიღებთ იმ დღეს, რასაც ბანკი წერს.

6. **საერთო ჯამები ვერ ამჩნევს კატეგორიების გაყრას.** როცა ჩანაწერი ერთი
   კატეგორიიდან მეორეში გადადის, არც რაოდენობა იცვლება და არც ჯამი.
   შემოწმებამ **კატეგორიების დაშლაც** უნდა შეადაროს, პირდაპირ ჩანაწერებს.

7. **გადათვლა ორჯერ არაფერს უნდა ცვლიდეს.** `dedup_key` ბანკის საკუთარი
   ID-ია, ჩაწერა დუბლიკატებს უგულებელყოფს. გაწყვეტილი გაშვება სწორდება
   თავიდან გაშვებით.

8. **ჩავარდნილი ბანკის ნიშნული არ იძვრება.** თორემ მომდევნო გაშვება იმ
   პერიოდს გამოტოვებს.

9. **ბანკები უკანა რიცხვით ამატებენ.** ყოველი გაშვება ნიშნულამდე 7 დღეს
   თავიდან კითხულობს.

10. **მობილურზე დიდი ციფრები არ უნდა გადიოდეს ეკრანს.** CSS grid
    `minmax(0,1fr)` + `min-width:0` + `clamp()` შრიფტზე.

## 10. უსაფრთხოება

- **ბრაუზერში საიდუმლო არ ინახება.** გვერდის კოდი საჯაროა.
- **Client Secret** Supabase Vault-ში, დაშიფრულად. ცხრილი მხოლოდ
  მაჩვენებელს ინახავს.
- **ბრაუზერს სვეტების წაკითხვა დასახელებით აქვს მინიჭებული** და მაჩვენებელი
  მათ შორის არ არის — ანუ გასაღების წაკითხვის გზა არ არსებობს.
- **გაშიფვრის ფუნქცია** მხოლოდ `service_role`-ს აქვს — ანუ sync სერვისს.
- **sync სერვისი არასდროს უნდა იყოს ბრაუზერისთვის ხელმისაწვდომ ადგილას.**
- **მხოლოდ წაკითხვის** უფლების credentials. გადახდის უფლების — არასდროს.
- **ლოგებში credential არასდროს.** უარყოფილ credential-ზე პასუხი ხშირად
  თვითონ credential-ს იმეორებს — ლოგში მხოლოდ სტატუსი მიდის.
